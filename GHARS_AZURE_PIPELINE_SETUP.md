# Ghars Platform — Azure Pipelines with a self-hosted agent

How to build and deploy this application from Azure DevOps to a Windows/IIS server, using an
agent installed **on that server**. Follow the parts in order; each one ends in a state you can
verify before moving on.

Companion files:

| File | Purpose |
|---|---|
| [`azure-pipelines.yml`](azure-pipelines.yml) | The pipeline definition. Edit the `variables:` block to match your server. |
| [`deploy/Deploy-Ghars.ps1`](deploy/Deploy-Ghars.ps1) | What actually deploys. Runs standalone too, for incidents. |
| [`.config/dotnet-tools.json`](.config/dotnet-tools.json) | Pins `dotnet-ef` to 8.0.8 so the migration script is generated by a known version. |
| [`GHARS_PRODUCTION_OPERATIONS.md`](GHARS_PRODUCTION_OPERATIONS.md) | Storage, backup, permissions, migrations. The deploy script implements §2.3, §6.1 and §6.3. |
| [`GHARS_PRODUCTION_DEPLOYMENT_CHECKLIST.md`](GHARS_PRODUCTION_DEPLOYMENT_CHECKLIST.md) | Operator checklist for the first go-live. |

## Topology

```
   You ──push──▶ GitHub (gul-dsc/ghars)
                     │
                     │  webhook
                     ▼
              Azure DevOps  ── queues job ──┐
              (no inbound access needed)    │
                                            │  agent polls out over HTTPS/443
   ┌────────────────────────────────────────▼──────────────────────────┐
   │  WEB SERVER (Windows Server + IIS + SQL Server)                   │
   │                                                                    │
   │   Azure Pipelines agent (Windows service)                          │
   │        ├── builds  → dotnet publish                                │
   │        └── deploys → Deploy-Ghars.ps1 → C:\inetpub\ghars           │
   └────────────────────────────────────────────────────────────────────┘
```

The agent **polls outward**. Azure DevOps never connects in, so no inbound port, no public IP and
no WinRM endpoint is required. Only outbound HTTPS from the server.

> **Note on the current remote.** This repository pushes to GitHub over `ssh.github.com:443`
> because port 22 is blocked on this network. That does not affect the pipeline: the agent clones
> over **HTTPS** with a token Azure Pipelines injects, so SSH is never used.

## Two facts about this application that shape the pipeline

Read these before changing anything in the deploy script.

**1. The upload roots live inside the deployed folder and exist nowhere else.**
`protected-uploads/` (KPI evidence, organization licences, programme attachments) and
`wwwroot/uploads/` (certificates, gallery, agenda and channel media, logos) are runtime business
data. They are excluded from Git, are **not** in a database backup, and are not reproducible by the
platform. `ProtectedFileStore.Root()` resolves to `{ContentRoot}/protected-uploads` from a constant,
so the folder cannot be relocated by configuration — it must be *excluded* from any mirror copy.
A `robocopy /MIR`, a Web Deploy profile with "remove additional files", or a container image swap
that misses this deletes the evidence behind approvals that have already been granted.

**2. The application migrates the database on startup.**
`Program.cs` calls `DbSeeder.SeedAsync`, which calls `db.Database.MigrateAsync()`. The schema
therefore changes the moment the app pool comes back, whether or not anyone asked. The pipeline
consequently: backs the database up **first**, then applies the generated idempotent script while
the site is offline, so a migration failure stops the deployment instead of leaving a running site
on a half-migrated database. By the time startup runs, its migration step is a no-op.

And the one that is not about the pipeline but will bite hardest if missed:
**`ASPNETCORE_ENVIRONMENT` must be `Production`.** Started in `Development`, the seeder creates ~42
demo accounts whose passwords are public in `SEED_CREDENTIALS.md` and in this repository's history.

## Part 1 — Create the Azure DevOps project and connect the code

1. Sign in at `https://dev.azure.com/` and create an organization if you do not have one.
2. **New project** → name it `Ghars Platform` → **Private** → Work item process: whatever you use.
3. Decide where the code lives:
   - **Keep it on GitHub** (recommended — it is already there). Nothing to do yet; Part 7 creates
     the GitHub connection when you create the pipeline.
   - **Or move it to Azure Repos**: create the repo in **Repos**, then from your workstation:
     ```powershell
     git remote add azure https://dev.azure.com/<org>/Ghars%20Platform/_git/ghars
     git push azure main
     ```

**Verify:** the project opens and **Repos** shows your code (or GitHub still has `main` at the
commit you expect).

## Part 2 — Create the agent pool and a registration token

1. **Organization settings** (bottom-left) → **Agent pools** → **Add pool**.
2. Pool type **Self-hosted**, name **`Ghars-SelfHosted`**, tick **Grant access permission to all
   pipelines**, then **Create**.
3. Create the Personal Access Token the agent registers with:
   **User settings** (top-right avatar) → **Personal access tokens** → **New Token**.
   - Name: `ghars-agent-registration`
   - Scopes: **Custom defined** → **Agent Pools → Read & manage** (nothing else)
   - Expiry: 30 days is plenty — see below.
4. Copy the token. It is shown once.

> The token is used **only at registration**. The agent then holds its own credentials, so the PAT
> expiring later does not take the agent offline, and you should not store it anywhere afterwards.

**Verify:** the pool `Ghars-SelfHosted` exists and shows zero agents.

## Part 3 — Prepare the server

Run everything in this part in an **elevated PowerShell** on the web server.

### 3.1 IIS and its features

```powershell
Install-WindowsFeature -Name `
    Web-Server, Web-Asp-Net45, Web-WebSockets, `
    Web-Mgmt-Console, Web-Scripting-Tools `
    -IncludeManagementTools
```

- `Web-WebSockets` — SignalR (`/hubs/notifications`) needs it; without it notifications silently
  fall back to long polling.
- `Web-Scripting-Tools` — provides the `WebAdministration` PowerShell module the deploy script uses
  to stop and start the app pool. Missing it is the most common first-run failure.

### 3.2 .NET

Install in this order:

1. **.NET 8 Hosting Bundle** — <https://dotnet.microsoft.com/download/dotnet/8.0> → "Hosting Bundle".
   This installs the runtime **and** the ASP.NET Core Module v2 that IIS needs.
2. **.NET 8 SDK** — needed because the agent builds on this machine.
3. `iisreset`

> Order matters. Installing the Hosting Bundle *before* IIS leaves the module unregistered and every
> request returns **HTTP 500.19**. If that happens, repair the Hosting Bundle and `iisreset`.

```powershell
dotnet --list-sdks       # expect an 8.0.x entry
dotnet --list-runtimes   # expect Microsoft.AspNetCore.App 8.0.x
```

### 3.3 sqlcmd

The deploy script uses `sqlcmd` for the pre-deploy backup and the migration script. Install the
**SQL Server Command Line Utilities** if it is not already present (it is, if SQL Server tooling is
installed on this box), then:

```powershell
sqlcmd -S . -E -C -Q "SELECT @@VERSION"
```

### 3.4 A service account

Create (or nominate) an account for the agent service. It needs to:

| Needs to | Grant |
|---|---|
| Write to `C:\inetpub\ghars` | NTFS Modify, or local Administrators |
| Stop/start the app pool | Local **Administrators** |
| `BACKUP DATABASE` and apply DDL | SQL login mapped to **`db_owner`** on `GharsPlatformDb` |

```sql
CREATE LOGIN [DOMAIN\svc-ghars-deploy] FROM WINDOWS;
USE GharsPlatformDb;
CREATE USER [DOMAIN\svc-ghars-deploy] FOR LOGIN [DOMAIN\svc-ghars-deploy];
ALTER ROLE db_owner ADD MEMBER [DOMAIN\svc-ghars-deploy];
```

> This account can change production. Use a dedicated one, not a person's account, and not one that
> is also used by the application.

### 3.5 Outbound network

Allow HTTPS/443 out to: `dev.azure.com`, `*.dev.azure.com`, `*.visualstudio.com`,
`*.vsassets.io`, `api.nuget.org`, and `github.com` + `codeload.github.com` if the code stays on
GitHub. Behind a proxy, pass `--proxyurl http://proxy:8080` to `config.cmd` in Part 4.

**Verify:**
```powershell
Test-NetConnection dev.azure.com -Port 443
Test-NetConnection github.com    -Port 443
```

## Part 4 — Install the agent on the server

1. In Azure DevOps: **Agent pools → Ghars-SelfHosted → New agent → Windows → x64 → Download**.
   Copy the zip to the server.
2. Elevated PowerShell on the server:

   ```powershell
   New-Item -ItemType Directory -Force -Path C:\azagent\A1
   Set-Location C:\azagent\A1
   Add-Type -AssemblyName System.IO.Compression.FileSystem
   [IO.Compression.ZipFile]::ExtractToDirectory("$HOME\Downloads\vsts-agent-win-x64-<version>.zip", $PWD)
   .\config.cmd
   ```

   > Put the agent at a **short path** like `C:\azagent\A1`. Deep paths plus the agent's `_work`
   > folder plus `obj\Release\net8.0\...` will hit the 260-character path limit during restore.

3. Configure it. **Use the unattended form** — the interactive prompts for *pool* and *agent name*
   are adjacent and easy to transpose, and getting them the wrong way round registers a correctly
   named agent into the wrong pool without any error:

   ```powershell
   .\config.cmd --unattended `
       --url https://dev.azure.com/<your-org> `
       --auth pat --token <the PAT from Part 2> `
       --pool Ghars-SelfHosted `
       --agent GHARS-WEB01 `
       --work _work `
       --runAsService `
       --windowsLogonAccount "DOMAIN\svc-ghars-deploy" `
       --windowsLogonPassword "<password>" `
       --replace
   ```

   - `--runAsService` **requires an elevated prompt**. Without it, configuration gets as far as
     "Settings Saved" and then fails with *"Needs Administrator privileges for configuring agent
     as windows service"* — the agent is registered but has no service.
   - The pool must already exist (Part 2). `--pool` does not create it.
   - The password appears in your PowerShell history. Clear it afterwards
     (`Remove-Item (Get-PSReadlineOption).HistorySavePath`) or configure interactively instead.
   - Omitting `--windowsLogonAccount` runs the service as `NT AUTHORITY\NETWORK SERVICE`, which
     cannot stop the app pool — the deploy stage will fail. See §3.4.

   Interactive equivalent, if you prefer the prompts:

   | Prompt | Answer |
   |---|---|
   | Server URL | `https://dev.azure.com/<your-org>` |
   | Authentication type | `PAT` |
   | Personal access token | the token from Part 2 |
   | **Enter agent pool** | **`Ghars-SelfHosted`** ← the pool, not the machine |
   | **Enter agent name** | **`GHARS-WEB01`** ← the machine, not the pool |
   | Work folder | `_work` (default) |
   | Run agent as service? | **`Y`** |
   | User account | `DOMAIN\svc-ghars-deploy` (from §3.4) |
   | Prevent service starting immediately? | `N` |

### Reconfiguring after a mistake

`config.cmd` refuses to run against an already-configured agent. Deregister first, from an
**elevated** prompt, then configure again:

```powershell
cd C:\agent
.\config.cmd remove --unattended --auth pat --token <PAT>
```

If `remove` cannot reach the server, delete the agent in the portal instead — **Agent pools →
\<pool\> → Agents → \<agent\> → Delete** — then delete `.agent` and `.credentials` from the agent
folder before reconfiguring.

**Verify:** the pool page shows `GHARS-WEB01` as **Online** (green). Locally:

```powershell
Get-Service vstsagent* | Format-Table Name, Status, StartType
```

## Part 5 — One-time IIS site setup

Still elevated, on the server.

### 5.1 Folders, app pool, site

```powershell
Import-Module WebAdministration

New-Item -ItemType Directory -Force -Path C:\inetpub\ghars
New-Item -ItemType Directory -Force -Path C:\inetpub\ghars\wwwroot\uploads
'kpi','org','surveys','programs' | ForEach-Object {
    New-Item -ItemType Directory -Force -Path "C:\inetpub\ghars\protected-uploads\$_"
}
New-Item -ItemType Directory -Force -Path D:\GharsBackups\predeploy, D:\GharsReleases

New-WebAppPool -Name GharsPlatform
# "No Managed Code" - the .NET Framework CLR is not loaded into the worker process. The published
# web.config uses hostingModel="inprocess", so the application itself runs inside w3wp.
Set-ItemProperty IIS:\AppPools\GharsPlatform -Name managedRuntimeVersion -Value ''
# Startup runs migrations and seeding, so do not let the pool idle out and pay that on a user request.
Set-ItemProperty IIS:\AppPools\GharsPlatform -Name startMode -Value AlwaysRunning
Set-ItemProperty IIS:\AppPools\GharsPlatform -Name processModel.idleTimeout -Value ([TimeSpan]::Zero)
Set-ItemProperty IIS:\AppPools\GharsPlatform -Name recycling.periodicRestart.time -Value ([TimeSpan]::Zero)

# Port 89: port 80 on this server belongs to a different site. Adjust if yours differs, and keep
# azure-pipelines.yml's healthUrl in step with it.
New-Website -Name Ghars -PhysicalPath C:\inetpub\ghars -ApplicationPool GharsPlatform -Port 89 -Force
Set-ItemProperty IIS:\Sites\Ghars -Name applicationDefaults.preloadEnabled -Value True
```

> **Do not put the site root under another site's root.** `C:\inetpub\wwwroot` is the Default Web
> Site's physical path, so a site rooted at `C:\inetpub\wwwroot\ghars` leaves
> `…\ghars\protected-uploads\` inside the Default Web Site's file system namespace. Creating a
> separate *site* does not carve the folder out of it. The moment Default Web Site is started,
> `http://<server>/ghars/protected-uploads/kpi/<guid>.pdf` is served straight off disk by the
> static file handler, bypassing `ProtectedFilesController` and every permission check in it —
> exactly the "published as a virtual directory or static-file mapping" that operations §2.3
> forbids. Use a path outside `C:\inetpub\wwwroot`, such as `C:\inetpub\ghars`.

### 5.1.1 Sharing the server with another site

This server already hosts another site on port 80. Two things must be true, and neither is
automatic:

**The two sites must not share an application pool.** The deployment stops the pool for the
duration of the copy. If the other site runs in the same pool, every Ghars deployment takes that
site down too — silently, and with no mention of it in the pipeline log.

```powershell
Get-Website | Select-Object Name, State, applicationPool,
    @{n='Bindings'; e={ ($_.Bindings.Collection | ForEach-Object BindingInformation) -join ' | ' }}
```

Every row except `Ghars` must show an `applicationPool` other than `GharsPlatform`.

**`iisreset` restarts every site on the box.** §3.2 needs one after installing the Hosting Bundle,
so schedule it — or restrict the restart to the one pool once the bundle is already in place:

```powershell
Restart-WebAppPool -Name GharsPlatform     # affects only Ghars
```

### 5.1.2 HTTPS

`Program.cs` calls `UseHttpsRedirection()` and `UseHsts()`. With an HTTP-only binding the
redirection middleware cannot determine a target port, so it logs *"Failed to determine the https
port for redirect"* once and passes every request through. **The site will work on
`http://<host>:89` — it will not loop, and it will not redirect.**

That is worth being deliberate about rather than discovering later: this application authenticates
with an ASP.NET Core Identity cookie and carries KPI evidence, licences and participant
certificates. Over plain HTTP the session cookie crosses the network in the clear. Acceptable on an
isolated internal segment; not acceptable if the port is reachable more widely.

To add HTTPS, bind a certificate on a free port (443 may already belong to the other site — check
the binding list above):

```powershell
New-WebBinding -Name Ghars -Protocol https -Port 8443 -HostHeader <your-host> -SslFlags 1
# Server Name Indication (-SslFlags 1) lets two sites share a port with different host names.
(Get-ChildItem Cert:\LocalMachine\My | Where-Object Subject -match '<your-host>')[0] |
    New-Item -Path "IIS:\SslBindings\!8443!<your-host>" -SSLFlags 1
```

Then point `healthUrl` in [`azure-pipelines.yml`](azure-pipelines.yml) at the HTTPS URL, so the
smoke test exercises what users actually hit.

### 5.2 Configuration — as app pool environment variables

`dotnet publish` regenerates `web.config` on every deploy, so **do not** put settings there. App
pool environment variables live in `applicationHost.config` and survive redeployment.

```powershell
$appcmd = "$env:SystemRoot\system32\inetsrv\appcmd.exe"

& $appcmd --% set config -section:system.applicationHost/applicationPools /+"[name='GharsPlatform'].environmentVariables.[name='ASPNETCORE_ENVIRONMENT',value='Production']" /commit:apphost

& $appcmd --% set config -section:system.applicationHost/applicationPools /+"[name='GharsPlatform'].environmentVariables.[name='ConnectionStrings__DefaultConnection',value='Server=.;Database=GharsPlatformDb;Trusted_Connection=True;TrustServerCertificate=True;MultipleActiveResultSets=true']" /commit:apphost
```

The `--%` stops PowerShell from parsing the rest of the line, so `appcmd`'s bracket syntax arrives
intact. Read them back with:

```powershell
& $appcmd --% list config -section:system.applicationHost/applicationPools
```

Using `Trusted_Connection` means the **app pool identity** connects to SQL. For the default
`ApplicationPoolIdentity` on a local instance, grant `IIS APPPOOL\GharsPlatform` a login and the
`db_datareader`/`db_datawriter`/`db_ddladmin` roles (or `db_owner`, since startup migrates). For a
*remote* SQL Server, switch the app pool identity to a domain account — a machine-local
`ApplicationPoolIdentity` cannot authenticate off-box.

`appsettings.Production.json` is an alternative for non-secret overrides. It is gitignored and the
deploy script excludes it from the mirror, so a copy placed on the server survives deployments.

### 5.3 Bootstrap administrator — first deployment only

Only if the database is new and has no administrator (per operations §6.2 step 5):

```powershell
& $appcmd --% set config -section:system.applicationHost/applicationPools /+"[name='GharsPlatform'].environmentVariables.[name='GHARS_BOOTSTRAP_ADMIN_EMAIL',value='admin@dubaisc.ae']" /commit:apphost
& $appcmd --% set config -section:system.applicationHost/applicationPools /+"[name='GharsPlatform'].environmentVariables.[name='GHARS_BOOTSTRAP_ADMIN_PASSWORD',value='<one-time password>']" /commit:apphost
```

**Remove both after the first sign-in and password change** (operations §6.2 step 8):

```powershell
& $appcmd --% set config -section:system.applicationHost/applicationPools /-"[name='GharsPlatform'].environmentVariables.[name='GHARS_BOOTSTRAP_ADMIN_PASSWORD']" /commit:apphost
```

Never put this password in a pipeline variable, and never commit it.

### 5.4 Permissions

```powershell
$app = "IIS AppPool\GharsPlatform"

icacls C:\inetpub\ghars /grant "${app}:(OI)(CI)(RX)"
icacls C:\inetpub\ghars\wwwroot\uploads /grant "${app}:(OI)(CI)(M)"

# Inherit-and-restrict, per operations 2.3.
icacls C:\inetpub\ghars\protected-uploads /inheritance:r
icacls C:\inetpub\ghars\protected-uploads /grant "${app}:(OI)(CI)(M)"
icacls C:\inetpub\ghars\protected-uploads /grant "Administrators:(OI)(CI)(F)"
```

The deploy script re-applies the `protected-uploads` ACL on every run, because a folder recreated by
a restore or a copy is the most likely way that protection is quietly lost.

**Never** map `protected-uploads` as a virtual directory, alias, or static file location.

### 5.5 Upload size (check this before go-live)

IIS caps request bodies at ~28.6 MB by default and the application sets no override. If KPI evidence
or programme attachments exceed that, uploads fail with **HTTP 404.13**. Because publish regenerates
`web.config`, the fix belongs in a `web.config` committed to the *project* — the SDK merges its
`aspNetCore` element into your file rather than replacing it:

```xml
<system.webServer>
  <security>
    <requestFiltering>
      <requestLimits maxAllowedContentLength="104857600" /> <!-- 100 MB -->
    </requestFiltering>
  </security>
</system.webServer>
```

## Part 8 — Environment (and an optional approval gate)

**Nothing to do here to get running.** The `deployment: DeployIIS` job names the environment
`Ghars-Production`, and Azure DevOps creates it on the first run if it does not already exist. The
environment is what records which build reached production and when — that part is automatic.

What is *not* automatic is the approval. As configured, **every push to `main` deploys unattended**.
That is a deliberate choice here, not an oversight. To add a gate later:

1. **Pipelines → Environments → `Ghars-Production`**.
2. **⋮ → Approvals and checks → Approvals**.
3. Add the approvers, and under Advanced clear "Allow approvers to approve their own runs".

The deploy stage then pauses until someone approves, and records who released what.

Worth revisiting if the trigger ever widens beyond `main`, or once the platform carries live club
data — an unattended deployment also applies schema migrations on startup.

### 8.1 Migrations carried by recent releases

Each release that changes the schema is listed here with what it does, so the state a production
database should be in after a deployment can be checked against a name rather than inferred.
Migrations apply automatically on startup; the pipeline additionally publishes an idempotent script
in the artifact (`migrations/ghars-migrations.sql`) so the change can be read before it is applied.

| Migration | What it adds | Data impact |
|---|---|---|
| `20260911151258_AddPartnerAvailabilityCalendar` | Table `PartnerAvailabilitySlots` (17 columns, 4 indexes, 3 foreign keys) and the nullable column `BookingRequests.PartnerAvailabilitySlotId` with its foreign key | **Additive only.** No existing column is altered or dropped. Every existing booking keeps `PartnerAvailabilitySlotId = NULL` and nothing is back-filled. Expected shape afterwards: 16 migrations / 53 tables / 647 columns on a database built from scratch — see operations §6.3. |

> `UX_PartnerAvailabilitySlots_ActiveUnique` is a **filtered** index. Anything that runs the
> migration script by hand needs `QUOTED_IDENTIFIER ON` — `sqlcmd -I`. The script the pipeline
> publishes already contains many such statements; this adds to that set rather than introducing
> the requirement.

## Part 9 — First run

1. **Pipelines → Ghars Platform → Run pipeline** → branch `main` → **Run**.
2. Watch the **Build** stage. Expect **0 errors and 1 warning** — `Models/Core/Activity.cs(103,19)`
   CS0108 is known and deliberate; it is not suppressed and must not be turned into an error.
3. Approve the **Deploy** stage. The log walks its own steps: validate → backup → snapshot →
   offline → migrate → mirror → online → smoke test.
4. The smoke test asserts `GET /` returns 200 **and** that four protected paths return 404. A 200 on
   any of those fails the deployment — protected evidence would be served straight off disk.

Then confirm production seeding did the right thing (operations §6.2 step 9):

```sql
SELECT COUNT(*) FROM AspNetUsers WHERE Email LIKE '%@ghars.local';  -- expect 0
SELECT COUNT(*) FROM AspNetRoles;                                   -- expect 7
SELECT COUNT(*) FROM Seasons WHERE IsActive = 1;                    -- expect 1
```

Any `@ghars.local` account means the application started in `Development`. Those passwords are
public. Delete the accounts and rotate anything they could reach.

The startup log on a correct production start says:
`Demo/sample seeding skipped: environment is Production, not Development.`

## Part 10 — Rollback

Every deployment snapshots the previous build to `D:\GharsReleases\rollback-<timestamp>` (binaries
and views only — the upload roots are never copied). To go back:

```powershell
cd C:\azagent\A1\_work\<n>\ghars-drop\deploy   # or wherever you keep the script
.\Deploy-Ghars.ps1 `
    -Source "D:\GharsReleases\rollback-20260910-143000" `
    -SitePath C:\inetpub\ghars `
    -AppPool GharsPlatform `
    -AppPoolIdentity "IIS AppPool\GharsPlatform" `
    -HealthCheckUrl http://localhost:89/
```

**A code rollback does not roll back the schema.** If the release included a migration, the old
binaries will meet a newer database. Where that matters, restore the pre-deploy `.bak` from
`D:\GharsBackups\predeploy` — which is exactly why it is taken before anything else.

## Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Agent shows **Offline** | Service stopped, or outbound 443 blocked | `Get-Service vstsagent*`; check `C:\azagent\A1\_diag\*.log` |
| *"No hosted parallelism has been purchased"* | A job is on a Microsoft-hosted pool | Both `pool: name:` must be `Ghars-SelfHosted` |
| **HTTP 500.19** | Hosting Bundle missing, or installed before IIS | Repair the Hosting Bundle, then `iisreset` |
| **HTTP 500.30** | App started and crashed — usually the connection string | Set `stdoutLogEnabled="true"` in `web.config`, reproduce, then read `logs\stdout_*.log`. Turn it back off. |
| **HTTP 500.31** | ASP.NET Core 8 runtime not found | Install the Hosting Bundle |
| **HTTP 404.13** on upload | IIS 28.6 MB request cap | §5.5 |
| `Import-Module WebAdministration` fails | IIS Management Scripts and Tools missing | `Install-WindowsFeature Web-Scripting-Tools` |
| Deploy fails, robocopy exit ≥ 8 | Files locked — the app pool did not stop | Confirm the agent account is a local Administrator |
| `sqlcmd` not recognised | Command line utilities not installed | §3.3 |
| Migration step fails on a **pre-2026-09-06** database | Four migrations have no history rows | Run the one-time `INSERT INTO __EFMigrationsHistory` in operations §6.3 **before** deploying |
| `dotnet dotnet-ef` not found | `dotnet tool restore` did not run, or `.config/dotnet-tools.json` was not committed | Confirm the manifest is in the repository and the restore step ran |
| Demo `@ghars.local` accounts appear | `ASPNETCORE_ENVIRONMENT` is not `Production` | §5.2, then delete the accounts and rotate |
| Notifications do not arrive live | WebSockets feature missing | `Install-WindowsFeature Web-WebSockets` |
| Path-too-long during restore | Agent installed under a deep path | Reinstall the agent at `C:\azagent\A1` |

---

## What is deliberately *not* in the pipeline

- **Secrets.** The connection string and bootstrap password are app pool environment variables on
  the server. Nothing secret is in this repository or in pipeline variables.
- **`dotnet ef database update`.** The pipeline applies a reviewed idempotent *script* instead, so
  the build agent never needs a live design-time connection to production.
- **Automatic deployment without approval.** The Environment gate in Part 8 is the control.
- **Touching the upload roots.** The deploy script only ever creates missing category folders and
  re-asserts their ACL. It never copies into them and never deletes from them.
